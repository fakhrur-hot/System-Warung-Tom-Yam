# APK Audit — Data Parsing & Design/Functionality Structure

**Date:** 2026-07-22
**Scope:** The Android app (`apk/`) only, focused on the two concerns you raised — (1) *"some information does not parse well"* and (2) *"design is not well structured with the functionality."* This complements the security-focused findings in [audit-report-2026-07-22.md](audit-report-2026-07-22.md) and does not repeat them.
**Method:** Direct read of the parsing layer (`ApiClient.kt`, `RealtimeService.kt`, `Converters.kt`, data entities), the navigation graph, and the Table View / ordering UI + view-models. No files modified.

---

## Executive summary

Your instinct is correct on both counts, and they have concrete root causes:

- **Parsing:** there is one specific, repeated bug — the `org.json` `optString(name, null)` idiom returns the literal string **`"null"`** (not a real null) whenever the server sends a JSON `null`. It affects payment method, notes, cancel reason, timestamps, device role/API key, and more, and the bad value is written straight into the local Room database and then shown in the UI and printed on slips. The same order payload is parsed **three separate times** by three hand-written parsers, all carrying this bug.
- **Design vs. functionality:** the app has **two nearly-identical Table View implementations** (admin vs. staff) that duplicate the grid, the status colors, the status enum, and the order-detail sheet; order **status is modeled two incompatible ways at once** (a typed enum for the grid, raw strings for the detail actions); and the admin home crams **11 unrelated destinations into a single overflow menu** with an inverted icon meaning. The structure doesn't cleanly map onto what the screens actually do.

## A. Data parsing — "some information does not parse well"

### P-1 (High) — `optString(name, null)` yields the string `"null"`, corrupting nullable fields
**Files:** [ApiClient.kt](../apk/app/src/main/java/com/warungtomyam/pos/data/ApiClient.kt) lines 151–152, 549, 551–553, 567, 604, 658; [RealtimeService.kt](../apk/app/src/main/java/com/warungtomyam/pos/realtime/RealtimeService.kt) lines 301, 303–305, 325; [TableViewViewModel.kt](../apk/app/src/main/java/com/warungtomyam/pos/ui/viewmodels/TableViewViewModel.kt) lines 422, 441.

Android's `JSONObject.optString(name, fallback)` returns the fallback **only when the key is absent**. When the key is *present but set to JSON `null`* — which is exactly how the backend represents an unpaid order's `paymentMethod`, a not-yet-sent order's `sentToKitchenAt`, an un-cancelled order's `cancelReason`/`cancelledBy`, an item with no `note`, or a still-`PENDING` device's `role`/`apiKey` — `opt()` returns the `JSONObject.NULL` sentinel and `optString` stringifies it to the literal **`"null"`**.

So these fields never become Kotlin `null`; they become the 4-character string `"null"`. Concretely:

- **`OrderItem.note`** — an item with no note is parsed as `note = "null"`. In [StaffTableViewScreen.kt:486](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/StaffTableViewScreen.kt#L486) the guard is `if (!item.note.isNullOrBlank())` — `"null"` is neither null nor blank, so the UI renders **`Note: null`** on every noteless item, and the kitchen-slip/receipt builders do the same on the printed ticket.
- **`Order.paymentMethod`** — an unpaid order carries `paymentMethod = "null"` instead of `null`, so any logic that checks "is this paid?" via `paymentMethod != null` is always true, and reports/aggregates that group by payment method get a bogus `"null"` bucket.
- **`Order.sentToKitchenAt` / `cancelReason` / `cancelledBy`** — all become `"null"`, breaking any "has this been sent?" / "was this cancelled?" null-check and showing `"null"` if surfaced.
- **`DeviceStatusResponse.role` / `apiKey`** — while a device is `PENDING`, `apiKey` parses as `"null"`; code that stores `secureStorage.setApiKey(response.apiKey)` could persist the string `"null"` as the API key.
- **`DeviceDto.lastSeenAt`** — `"null"` instead of null in the devices list.

The value is persisted to Room (`dao.insertOrder` / `insertOrderItems`), so it survives restarts and re-sync.

**Fix:** replace the idiom with an explicit null check, ideally via one shared helper:
```kotlin
fun JSONObject.optStringOrNull(name: String): String? =
    if (isNull(name)) null else optString(name)
```
and use `optStringOrNull("paymentMethod")` everywhere a nullable string is parsed. (Note: passing `null` as the second arg to `optString` is itself relying on a Java platform-type quirk to compile — the helper removes that too.)

### P-2 (Medium) — the same order payload is parsed by three separate hand-written parsers
**Files:** `ApiClient.parseOrderDto`/`parseOrderItemDto` ([ApiClient.kt:536–570](../apk/app/src/main/java/com/warungtomyam/pos/data/ApiClient.kt#L536)); the inline parser in `RealtimeService.handleNewOrderMessage` ([RealtimeService.kt:296–331](../apk/app/src/main/java/com/warungtomyam/pos/realtime/RealtimeService.kt#L296)); and a third mapping in `TableViewViewModel` (~lines 420–441).

An order coming from REST catch-up sync, from a WebSocket `NEW_ORDER` broadcast, and from the table-view mapping each goes through a different, independently-maintained block of `org.json` field reads. They already disagree in shape (the REST path builds `OrderDto` then maps to `Order`; the Realtime path builds the Room `Order`/`OrderItem` directly) and all three carry the P-1 bug. This is why one fix has to be applied in three places, and why a future backend field change will silently break whichever copy nobody remembered. **Fix:** extract one `Order.fromJson(JSONObject)` / `OrderItem.fromJson(JSONObject)` used by all three call sites.

### P-3 (Medium) — a single unexpected field silently drops the whole order
**Files:** [RealtimeService.kt:287–339](../apk/app/src/main/java/com/warungtomyam/pos/realtime/RealtimeService.kt#L287), and the `catch (e: Exception) { ApiResult.Error("PARSE_ERROR", …) }` blocks throughout `ApiClient`.

Required fields use `getString`/`getDouble`/`getInt`/`getBoolean`, which **throw** on any missing/mistyped field or on a JSON `null` in a "required" slot. In `handleNewOrderMessage` the surrounding `try/catch` logs and returns from the coroutine, so a single malformed field means the entire incoming order is dropped and **never appears on the kitchen Table View** — a silent data-loss path in the money flow. In `ApiClient` the same throw collapses to a generic `PARSE_ERROR` that the UI can't distinguish from a real parse failure vs. one unexpected null. **Fix:** decide per field whether it's truly required; tolerate nulls with the P-1 helper; and on the Realtime path, persist what parsed and log the offending field rather than discarding the order.

### P-4 (Low) — monetary values parsed as `Double`
**Files:** `total`, `unitPriceSnapshot` parsed via `getDouble(...)` in all three parsers; `MenuItem.price: Double`.

Prices and totals are floating-point end to end. For a POS this invites accumulation/rounding error (e.g. summing many line items, cash-vs-QR split reconciliation). Display uses `"%.2f".format(...)`, which hides but does not fix it. **Fix:** store money as integer sen/cents (or `BigDecimal`) and format at the edge. Low urgency for a small stall, but it's a latent correctness issue in the part of the app that handles money.

### P-5 (Low) — unvalidated enum-like strings accepted verbatim
`source` defaults to `"QR"` via `optString("source", "QR")` but any string the server sends is accepted; order `status` is likewise a free string (see D-2). There's no `when`-with-exhaustive-fallback at parse time, so an unrecognized value flows deep into the UI before it's noticed. **Fix:** map to a sealed/enum type at parse boundary with an explicit `UNKNOWN` case.

## B. Design / architecture — "not well structured with the functionality"

### D-1 (Medium) — two parallel Table View stacks duplicating grid, colors, status, and sheet
**Files:** [AdminHomeScreen.kt](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/AdminHomeScreen.kt) + [TableViewViewModel.kt](../apk/app/src/main/java/com/warungtomyam/pos/ui/viewmodels/TableViewViewModel.kt) vs. [StaffTableViewScreen.kt](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/StaffTableViewScreen.kt) + [StaffOrderViewModel.kt](../apk/app/src/main/java/com/warungtomyam/pos/ui/viewmodels/StaffOrderViewModel.kt).

`TableCell` and `StaffTableCell` are byte-for-byte the same layout and the same 5-color status map (`FREE`→green, `RECEIVED`→orange, `SENT_TO_KITCHEN`→red, `PREPARING`→purple, `READY`→blue). Each view-model independently declares its own `TableStatus` enum, `TableState`, and `OrderDetailState`. The order-detail bottom sheet is reimplemented in each. The two screens differ only in a few RBAC gates and the check-out button. This is the clearest "design not structured with the functionality" symptom: the same feature exists twice, so any fix (a color, a status, a payment rule) must be made in two places and will drift. **Fix:** one shared `TableGrid`/`TableCell` composable + one shared `OrderStatus` enum + a shared `OrderDetailSheet`, parameterized by a permissions object.

### D-2 (Medium) — order status is modeled two incompatible ways at once
**Files:** `TableStatus` enum ([TableViewViewModel.kt:48](../apk/app/src/main/java/com/warungtomyam/pos/ui/viewmodels/TableViewViewModel.kt#L48)) used for grid coloring, vs. raw string comparisons in the detail sheet ([StaffTableViewScreen.kt:420, 433, 443–444](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/StaffTableViewScreen.kt#L420): `order.status != "COMPLETED"`, `== "RECEIVED"`, `!= "CANCELLED"`).

The grid uses a typed enum of 5 states; the action buttons switch on stringly-typed status values — and the string set includes `"COMPLETED"` and `"CANCELLED"`, which **don't exist in the `TableStatus` enum at all**. So there are two disjoint definitions of "what states can an order be in," neither complete, and the compiler can't catch a typo like `"CANCELED"` vs `"CANCELLED"`. Payment/kitchen buttons are gated by hand-written string inequalities rather than a state machine, even though the order lifecycle *is* a state machine (RECEIVED → SENT_TO_KITCHEN → PREPARING → READY → COMPLETED, plus CANCELLED). **Fix:** a single `enum class OrderStatus` with a Room `TypeConverter` (today `Converters` only handles printer enums — [Converters.kt](../apk/app/src/main/java/com/warungtomyam/pos/data/local/Converters.kt)), and derive both the grid color and the allowed actions from it.

### D-3 (Medium) — admin home information architecture: 11 destinations in one overflow menu
**File:** [AdminHomeScreen.kt:132–217](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/AdminHomeScreen.kt#L132).

The single `DropdownMenu` holds New Dine-In Order, Devices, Printers, Menu Management, Generate QR Cards, Reports, Backup, Background Setup, Settings, Sign Out, **and** Sign Out with Closing — 11 items, mixing frequent operational actions, rare setup screens, and the two destructive sign-out actions in one flat, unlabeled list. Two structural problems:
- The **primary** action on a POS home ("start a new order") is buried at the bottom of an overflow menu, while the top-bar **`+` (Add) icon** is wired to *table management* ([line 129](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/AdminHomeScreen.kt#L129)) — the icon most users read as "new order" does the least-used thing.
- Sign-out (session-ending, hard to undo) sits adjacent to ordinary navigation with no separation or confirmation affordance.

**Fix:** promote New Dine-In to a visible action/FAB (the staff screen already uses a FAB for exactly this — another inconsistency); group setup screens (Devices/Printers/Menu/QR/Backup/Background/Settings) under a "Setup" section; separate the sign-out actions.

### D-4 (Medium) — Add/Edit menu item overloaded via an empty-string sentinel
**File:** [AppNavGraph.kt:169–183](../apk/app/src/main/java/com/warungtomyam/pos/ui/navigation/AppNavGraph.kt#L169).

The Edit route reuses `AddMenuItemScreen` and passes `category = ""` with the comment *"Look up item's category — form will load from existing item."* Mode ("am I adding or editing?") is encoded as *empty string vs. non-empty*, and the edit path deliberately discards the category argument and relies on the screen to re-fetch it. This is fragile (an add with a legitimately empty category would be misread) and hides the add/edit distinction from the type system. **Fix:** an explicit `mode` nav argument or two distinct screen entry points with a shared form composable.

### D-5 (Low) — inconsistent DI: one screen uses `viewModel()`, the rest use `hiltViewModel()`
**File:** [OrderingHomeScreen.kt:40](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/OrderingHomeScreen.kt#L40) uses androidx `viewModel()`, whereas `AdminHomeScreen`, `StaffTableViewScreen`, etc. use `hiltViewModel()`. This ties into the hand-rolled service-locator that `OrderingViewModel`/`OrderingForegroundService` use instead of Hilt (also noted in the security audit's L-2). Two DI styles in one module raises the chance a future dependency is wired in one path but forgotten in the other. **Fix:** make `OrderingViewModel` a `@HiltViewModel` and the services `@AndroidEntryPoint`.

### D-6 (Low) — status color semantics are counter-intuitive and unlabeled
**File:** [AdminHomeScreen.kt:352–358](../apk/app/src/main/java/com/warungtomyam/pos/ui/screens/AdminHomeScreen.kt#L352) (and the staff copy).

`SENT_TO_KITCHEN` is **red** — the color operators read as "problem/urgent" — for a perfectly normal in-progress state, while `READY` (the state that most needs staff attention to serve/clear) is a low-urgency **blue**. There's also no legend anywhere on the grid, so the color→state mapping is unexplained. For an at-a-glance POS grid this inverts the visual priority. **Fix:** reserve red/high-contrast for the state needing action (READY), and add a small legend or per-cell status text (the text is already there — lean on it).

### D-7 (Low) — Room type-converters cover only printer enums, not order/table status
**File:** [Converters.kt](../apk/app/src/main/java/com/warungtomyam/pos/data/local/Converters.kt) converts `PaperWidth` and `PrinterRole` only. Order/table status is stored as a raw `String`, which is the storage-layer expression of D-2. Once D-2 introduces an `OrderStatus` enum, add its converter here for consistency and to reject invalid persisted values.

## C. Minor data-quality note — food dictionary

**File:** [FoodDictionary.kt](../apk/app/src/main/java/com/warungtomyam/pos/data/FoodDictionary.kt). The curated translation table is generally reasonable and the English-fallback design is sound, but a couple of entries are out of place for a food autocomplete and will show up as suggestions in admin menu entry: `"Racun"` (poison / 毒药 / พิษ, [line 149](../apk/app/src/main/java/com/warungtomyam/pos/data/FoodDictionary.kt#L149)) and `"Haram"` (forbidden, [line 143](../apk/app/src/main/java/com/warungtomyam/pos/data/FoodDictionary.kt#L143)). Several non-Malay entries are transliterations rather than translations (e.g. some Tamil terms are phonetic), which is acceptable under the fallback policy but means dictionary coverage/quality is uneven. Low priority — worth a cleanup pass if the autocomplete is user-facing.

## Suggested order of work

1. **P-1** — the one-line `optStringOrNull` helper + swapping the call sites. Highest impact for lowest effort; directly fixes the visible "Note: null" and the corrupted payment/cancel state. Do this first.
2. **P-2 / P-3** — while touching those call sites, collapse the three parsers into one shared mapper and make the Realtime path tolerant instead of order-dropping.
3. **D-2** — introduce a single `OrderStatus` enum + Room converter; it's the keystone that also simplifies D-1 and D-7.
4. **D-1** — extract the shared Table View composable + detail sheet on top of the new enum.
5. **D-3 / D-4** — IA cleanup on admin home and the add/edit route.
6. **D-5 / D-6 / D-7 / C** — consistency and polish.
